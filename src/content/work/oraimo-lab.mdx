<Section n="01" title="The problem">

I wanted my own companion app for the Oraimo Watch 6R: custom watch faces first, then health data. Nobody publishes the watch's service UUIDs, characteristic UUIDs, packet framing, checksum scheme or watch-face format. The official Oraimo Health app knows them; I don't.

The tempting move is to guess a format from a few packets and start building on it. A wrong guess looks exactly like knowledge, gets built on, and is expensive to unwind.

<Aside>The repository's protocol status page currently reads "What is known: Nothing." That's deliberate.</Aside>
</Section>

<Section n="02" title="The rule: evidence before decoders">

So the app is a lab first. It scans, connects, browses the attribute database, pokes individual characteristics and records every byte that moves, with a timestamp and a direction. There's no `decodePacket()` and no protocol constants anywhere.

Interpretation lives in a separate **evidence ledger**. An *observation* is something seen in a capture. A *hypothesis* is what it might mean, plus what would disprove it. Both must cite the packet rows they rest on, and a hypothesis only reaches `SUPPORTED` after a capture designed to break it fails to. Disproven hypotheses are kept: knowing what the protocol is *not* narrows the search.

<Aside>Try it in the playground above: cite packets and watch the ledger refuse claims the evidence doesn't back.</Aside>
</Section>

- **Recording can't be skipped.** Logging lives in a decorator around the transport, not at call sites, so no future edit can quietly stop an operation being recorded. A failed operation is recorded as a packet, with the platform's verbatim error, before the exception is rethrown.
- **The transport is an interface.** That's what lets the connection state machine (backoff, give-up path, not retrying into a switched-off radio) be tested against a fake radio.
- **Sessions are experiments.** `watchface-A`, `change-time`: each records the device, the times, my notes, and whether the evidence is ours or the official app's.

</Section>

<Section n="04" title="The hardest part: reading the official app's traffic">

The only way to see what Oraimo Health actually sends is Android's `btsnoop_hci.log`. The importer is pure Dart with no Flutter dependency, so it can be tested exhaustively against byte-level fixtures.

A watch-face image is far bigger than one Bluetooth packet, so it arrives as many ACL fragments that have to be reassembled into L2CAP frames before the ATT layer makes sense. The parser tracks reassembly per connection handle, keeps the channel ID from the fragment that started the frame, and handles traffic from two devices interleaved. If a capture starts part-way through a frame, the orphaned fragments are discarded, because inventing the missing start would be a fabrication. A handle stays unresolved unless the capture itself identified it.

<Aside>The parser tests are built from the Bluetooth spec, not from mocks: header validation, epoch conversion, reassembly across fragments, interleaved devices.</Aside>
</Section>

<Section n="05" title="Quality and where it's going">

- 156 tests and a CI job that runs `flutter analyze --fatal-infos` on every push. The JSON export schema is pinned by a golden test, because captures recorded by older builds must stay readable.
- The release APK asks only for Bluetooth permissions. With no INTERNET permission, captured evidence can't leave the phone except through an export you perform.
- **Next:** capture the official app installing a watch face, record observations, and move the first hypotheses to `SUPPORTED`. Only then does a protocol layer get written, on top of the transport, without either changing.

</Section>
